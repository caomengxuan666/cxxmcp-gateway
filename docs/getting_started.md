# Getting Started

This guide is for C++ hosts that want to embed `cxxmcp-gateway` as a library.
Use the gateway when your application already owns process lifecycle,
configuration, authentication, policy, deployment, or observability, but needs
MCP capability aggregation and request routing across multiple upstream
servers.

If you only need to write one MCP client or one MCP server, use the `cxxmcp`
SDK directly.

## Install and Link

Install an HTTP-enabled `cxxmcp` SDK first, then configure and install the
gateway against that SDK install tree:

```powershell
cmake -S . -B build -DCMAKE_PREFIX_PATH=C:\path\to\cxxmcp\install
cmake --build build
cmake --install build --prefix C:\path\to\cxxmcp-gateway\install
```

Downstream CMake projects should request the component they consume:

```cmake
cmake_minimum_required(VERSION 3.23)
project(my_gateway_host LANGUAGES CXX)

find_package(cxxmcp-gateway CONFIG REQUIRED COMPONENTS runtime)

add_executable(my_gateway_host main.cpp)
target_link_libraries(my_gateway_host PRIVATE cxxmcp-gateway::runtime)
target_compile_features(my_gateway_host PRIVATE cxx_std_23)
```

The umbrella header `<cxxmcp/gateway.hpp>` is core-only. Runtime consumers
should include `<cxxmcp/gateway/runtime.hpp>` and link
`cxxmcp-gateway::runtime`.

## Minimal Embedded Runtime

```cpp
#include <cxxmcp/gateway/config.hpp>
#include <cxxmcp/gateway/runtime.hpp>

#include <chrono>
#include <utility>

int main() {
  mcp::gateway::GatewayConfig config;
  config.name = "my-gateway";
  config.version = "1.0.0";

  mcp::gateway::UpstreamServer fs;
  fs.id = "fs";
  fs.transport = mcp::gateway::UpstreamTransportKind::process_stdio;
  fs.process_stdio.command = "filesystem-server";
  fs.process_stdio.args = {"--root", "."};
  fs.process_stdio.timeout = std::chrono::seconds{30};
  config.upstreams.push_back(std::move(fs));

  mcp::gateway::UpstreamServer tools;
  tools.id = "tools";
  tools.transport = mcp::gateway::UpstreamTransportKind::streamable_http;
  tools.streamable_http.uri = "http://127.0.0.1:3001/mcp";
  tools.streamable_http.timeout = std::chrono::seconds{30};
  config.upstreams.push_back(std::move(tools));

  auto valid = mcp::gateway::validate_gateway_config(config);
  if (!valid) {
    return 1;
  }

  mcp::gateway::GatewayRuntime runtime(std::move(config));
  auto started = runtime.start_http(
      {.host = "127.0.0.1", .port = 39931, .path = "/mcp"});
  if (!started) {
    return 1;
  }
  auto waited = runtime.wait();
  return waited.has_value() ? 0 : 1;
}
```

Downstream clients see one MCP endpoint at `http://127.0.0.1:39931/mcp`.
Tools and prompts are exposed as `<upstream>.<name>`, for example `fs.read` or
`tools.search`. Resources use gateway-owned URIs generated by the router.

## Recommended Host Flow

1. Build `GatewayConfig` from your own config source.
2. Call `validate_gateway_config()` before starting the runtime.
3. Optionally install a `GatewayRuntimeObserver` for lifecycle and upstream
   state events.
4. Optionally call `refresh_upstream_capabilities()` before `start_http()` when
   you want hosted capability advertisement to reflect initialized upstream
   capabilities.
5. Start the hosted Streamable HTTP endpoint with `start_http()`.
6. Call `stop()` during shutdown. Persistent upstream sessions are closed by
   `stop()`.

`clear_cached_catalogs()` invalidates successful aggregate tools/resources/
templates/prompts list caches. It does not close opt-in persistent upstream
sessions.

## Repeated-Call Latency

The default upstream session mode is `UpstreamSessionMode::per_call`. Each
upstream operation creates, initializes, uses, and stops an SDK client service.
That is the simplest lifecycle and is the default for correctness and
isolation.

Hosts that make repeated calls to the same upstream can opt into persistent
sessions:

```cpp
mcp::gateway::GatewayRuntimeOptions options;
options.upstream_session_mode =
    mcp::gateway::UpstreamSessionMode::persistent;

mcp::gateway::GatewayRuntime runtime(std::move(config), std::move(options));
```

Persistent mode keeps one initialized session per upstream and serializes
same-upstream calls through that session. It reduces repeated-call setup cost,
but it is not a connection pool and should not be presented as an ultra-low
latency or high-QPS multiplexing layer.

## Reference CLI

The `cxxmcp-gateway` executable is a thin reference runner:

```powershell
cxxmcp-gateway serve --port 39931 --upstream-http tools=http://127.0.0.1:3001/mcp
```

Use it for local development, smoke tests, demos, and simple sidecars. Product
hosts should prefer the runtime API above so they can own configuration,
credentials, policy, observability, and lifecycle.
